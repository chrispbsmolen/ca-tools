## Provenance of the verifier itself

caverify 0.2.0 is validated against a pure-R brute-force oracle
sharing no logic with the C kernel, and cross-validated against
CAs::coverage() with exact agreement required on verdicts, gapped
column sets, and missing-tuple counts: 3,541 randomized cases at the
run of record's kernel, including mixed-level arrays, NA-bearing
arrays, and arrays generated by CAs's own constructions, zero
mismatches (xval_mixed.R in this repository). The NA semantics were
corrected 2026-08-23 following a counterexample by Ulrike Groemping;
her example is a permanent regression test in the package.

## Three cyclotomy entries disputed, 2026-10-23

The November 2024 snapshot records CAN(3, 128, 6) = 762,
CAN(3, 2162, 20) = 43,220 and CAN(3, 2312, 21) = 48,531, each with
construction "Cyclotomy (Colbourn)". These are results of Colbourn,
Covering arrays from cyclotomy, Des. Codes Cryptogr. 55 (2010)
201-219, doi:10.1007/s10623-009-9333-8: Table 3 lists the three sizes
as new arrays, and Table 2 places q = 127 (v = 6), q = 2161 (v = 20)
and q = 2311 (v = 21) in the range where the cyclotomic vector has
property 3a of Construction 4.1, which gives CA(vq; 3, q + 1, v).

In August 2026 the CAs package's implementation of type 3a at these q
was found not to give covering arrays
(`../r/livingtable/findings/FINDING_CAN_3_128_6.md`): at q = 127 the
762 by 128 array leaves 5,334 of its 341,376 column triples uncovered
(caverify 0.2.0, 2026-08-29), and at q = 2161 and q = 2311 a 50-column
window of the array is not covered (2026-08-30). On 2026-09-04 the CAs
author changed these catalogue entries to type 4a (commit ae81661),
which adds a constant row and gives vq + v rows: 768, 43,240 and
48,552. The 768 by 128 array was verified in full
(`../r/livingtable/results/mac_4a_q127_result.txt`) and the two larger
ones screened on 48 column windows each
(`../r/livingtable/results/mac_4a_result.txt`).

On 2026-10-23 the paper itself was read and the properties were
recomputed from its own definitions (cyclotomic vector, Section 2;
Construction 4.1) by `../r/livingtable/cyclotomy_recheck.py`, whose
results a separate implementation reproduced (output in
`../r/livingtable/results/cyclotomy_recheck_result.txt`). At each of the three q the
vector meets every condition of type 3a except one: on some sets of
three columns the constant pattern (all three entries equal) never
occurs, even after the development modulo v. Type 4a supplies exactly
that pattern with its added constant row, so the vector has property
4a and not 3a. At q = 127 the script gives the same 5,334 uncovered
column triples for the 3a array as the August check, and a 768 by 128
type 4a array with none. This explains why the CAs fix works. The
result does not depend on the choice of primitive element (the paper
notes that another primitive element multiplies every entry by a unit
modulo v; the script checks two at q = 127, and the August check tried
all 36).

Recorded in the table on 2026-10-23: three DISPUTED rows, one per
entry, each with the same t, v, k and N as the CITED row, the type 3a
call that was checked as its recipe, and notes saying what failed. The
CITED rows are unchanged and still counted by the lookups. The 768 by
128 array, built with `CAs::bestCA(3, 128, 6, seed = 20260829)` (CAs
0.24-4, route CYCLOTOMY) and verified by caverify 0.2.0 on the Mac on
2026-10-23, was checked again with `ca_verify.c` (commit 50b439f) and
`tools/constant_rows.c` on a second machine (Linux x86_64): VERIFIED,
6 constant rows, file hash equal to the stamp. It is entered as a
VERIFIED S6 row with MANIFEST status above_snapshot. The two larger
type 4a arrays are not entered (screened only, and over 200 MB each
as text). None of this shows that the recorded sizes cannot be
reached by another construction.

## A strength-4 array from Theorem 6.2 of Shokri, Moura and Stevens, 2026-10-25

Theorem 6.2 of Shokri, Moura and Stevens (arXiv:2510.13122) builds a
CA(3q^4 + N(q - 2); 4, q^2 + 1, q) for an odd prime power q from any
CA(N; 3, (q^2+1)/2, q), and their Corollary 6.5 and Table 5 (Table 6
in v3) use N = 2q^3 - q, which gives CA(67782; 4, 122, 11) against the
snapshot's 70,521. The paper gives no array files. It was built here
with `../tools/sms_theorem62.py` (odd primes q). The strength-3
ingredient CA(2651; 3, 61, 11) has the size of their Theorem 3.4
(Torres-Jimenez and Izquierdo-Marquez 2018) but is not that array: the
script takes the two blocks of their Theorem 3.3, from a pair of
orthogoval planes over F_(q^3), keeps the first 61 points whose
coordinate vectors in both planes have a nonzero first entry, scales
each column within its block so that entry is 1 (the row given by c
e_0 is then the constant row c in both blocks), and removes the second
block's q constant rows. Scaling a column within a block does not
change which column sets that block covers, and every 3 of the points
are independent in one of the two planes, so the ingredient is a
strength-3 covering array; it was also verified directly.

| (t, k, v) | N | snapshot best | constant rows |
|---|---|---|---|
| (4, 122, 11) | 67,782 | 70,521 | 11 |

The array was verified in full twice: by caverify 0.2.0 on the Mac
(2026-10-25, 977 s, after rebuilding it there with the same script and
getting the same SHA-256) and by `ca_verify.c` on a second machine
(all 8,783,390 column 4-sets). The script's arrays for q = 3, 5 and 7
(294, 2610 and 10598 rows, the values of their Table 5) were verified
in full as well. An independent reimplementation, written without the
script, with other primitive polynomials, another linear functional
and a random choice of columns, gave verified arrays of the same sizes
for q = 3, 5 and 7 and a verified CA(2651; 3, 61, 11) (not stored).
Constant rows were counted by cafast::maxconstant_c.

## Three arrays from cyclic covering perfect hash families, 2026-10-28

A search written here (`../tools/cphf/symcphf.c`) looks for covering
perfect hash families CPHF(n; k, q, 5) whose columns are a cyclic group
of order k = (q^5 - 1)/(q - 1): in every row the vector of column c + 1
is a fixed matrix times the vector of column c. It found CPHF(11; 121,
3, 5), CPHF(13; 781, 5, 5) and CPHF(13; 2801, 7, 5), which give, by the
construction of Sherwood, Martirosyan and Colbourn (2006),
CA(2663; 5, 121, 3), CA(40613; 5, 781, 5) and CA(218479; 5, 2801, 7).
All three are smaller than the snapshot's best at their points: 3140,
46861 and 803022 (the rungs at k = 148, 914 and 2960). They improve the
table at k = 102 to 121, 501 to 781 and 1601 to 2801. The size 40613
is already in the snapshot at k = 500 (Torres-Jimenez and
Izquierdo-Marquez, restricted CPHF by simulated annealing), and the size
218479 at k = 1600 (CITED S7, Torres-Jimenez and Izquierdo-Marquez
2024); the new rows reach 281 and 1201 more columns at those sizes.

Checks:

- CA(2663; 5, 121, 3) is stored (`arrays/`, S8) and was verified in full
  with `ca_verify.c` (commit 441203c, 2026-10-27, Linux x86_64, about
  40 minutes on 2 threads: all 198,792,594 column sets cover all 243
  tuples). Its family was also checked by brute force over all 5-sets
  (`cphf_tools.c check`) and by `repcheck.c`.
- CA(40613; 5, 781, 5) and CA(218479; 5, 2801, 7) are 63 MB and about
  1.2 GB as text and are not stored. A full check of the arrays with
  `ca_verify.c` grows with C(k, 5) times N: from the 80 core-minutes of
  CA(2663; 5, 121, 3) it would be on the order of 10,000 core-days for
  the first and far more for the second. Their families are stored
  in `certificates/` and were checked exactly by `../tools/cphf/repcheck.c`,
  a program written for this check that shares no code with the search:
  it verifies for every row that one invertible matrix carries each
  column's vector to the next one (and the last to a nonzero multiple
  of the first), so that a set of columns and its cyclic shift are
  covered together, and then checks every one of the C(k - 1, 4) sets
  of 5 columns that contain column 0: 15,304,580,655 sets for k = 781
  (55 s, Linux x86_64) and 2,555,582,259,300 for k = 2801 (385 s on 14
  threads of an Apple Silicon MacBook Pro), all covered. A second,
  different CPHF(13; 2801, 7, 5) from another search run passed the same
  check (383 s) and is recorded in `../tools/cphf/RUNS.txt`, not stored.
- Before use, `repcheck.c` was tested against the brute force of
  `cphf_tools.c`: on a 9-row family with k = 121 that is not a CPHF,
  both find the same failures (875 representative sets, 21,175 sets in
  all), and a family with one entry changed fails the symmetry check.
- The rows' `array_sha256` is the hash of the array as
  `cphf_tools.c expand` writes it (0-based symbols, one run per line,
  the table's canonical form); `../tools/cphf/README.md` gives the
  commands to rebuild each array and compare.
