# A provenance-tracked table of best-known covering array sizes

First published 2026-08-23 as a dated snapshot; since 2026-10-18 a
living table that grows by pull request (`../submissions/README.md`).
It replaces folklore with evidence: every entry says where it came
from, and several hundred entries carry machine verification stamps
tied to explicit arrays you can check yourself. Improvements are not
yet propagated through recursive constructions: the engine in
`../r/livingtable` is run by hand and is not connected to
submissions, so no row here is derived by it.

The table covers strengths 2 to 6, alphabets of up to 25 symbols and
up to 100,000 columns (`../submissions/README.md`, "What the table
covers").

## What is here

- `ca_table.csv` - the table, append-only, one row per evidence
  event. Schema below.
- `ca_table.rda` - the same table as a compressed R data frame
  (object `ca_table`), regenerated from the CSV by
  `ca_table.R::make_rda()` automatically after every change.
- `ca_table.R`, `ca_table.py` - small query helpers for R and Python
  (best known N, stair-step, verified rows). No dependencies.
- `arrays/` - the explicit arrays in canonical form (0-based integer
  symbols, one run per line, space separated; `NA` marks a don't-care
  entry, see below). The MANIFEST `status` column separates arrays
  that equal the best-known size for their parameters at entry (`equals_best`)
  from those SMALLER than the November 2024 snapshot's recorded best
  (`exceeds_snapshot`). A third status, `above_snapshot` (since
  2026-10-23), marks an array larger than the snapshot's recorded best
  at its point, stored because that recorded value has a DISPUTED row
  (below). An array that comes through the submission check above the
  best known size at entry is stored with status `above_best`, and one
  that was screened rather than verified in full with status
  `screened`. File names are `CA_N_t_k_v.txt`, with a hash suffix
  where two distinct arrays share parameters. An array that came
  through the submission check and is larger than 1 MiB as text (since
  2026-11-01; before that, larger than 50 MiB) is stored compressed with
  gzip (`CA_N_t_k_v.txt.gz`, gzip header time 0 so the file is
  reproducible, readable by R's `read.table` and Python's `gzip` with
  nothing extra). Its MANIFEST hash is the hash of
  the uncompressed canonical text, and the self-test checks the
  decompressed bytes against it. The MANIFEST `status` of a screened
  array changes from `screened` to what the exact check found when a
  VERIFIED row is added beside its SCREENED row (since 2026-11-02 by an
  upgrade request, below under SCREENED), and `../tools/consistency.py`
  requires that no array with a VERIFIED row is still `screened`. A submitted array file is at most
  50 MiB as text, and a larger array stays in a public deposit and is
  listed in `EXTERNAL.csv` (below, and `../submissions/README.md`,
  "Size limits"). The recipe and
  the hash are always in the row. An array is stored when it equals or
  beats the best known size at entry, when it is the verified size
  beside a disputed entry, or when it came through the submission
  check; the other VERIFIED rows (those above the best known size at
  entry, the rows of the files in `withdrawn_files.csv`, and the rows
  whose array is given by a certificate in `certificates/`) carry the
  hash, stamp and recipe, so the array can be fetched or rebuilt again
  and checked against its hash.
- `withdrawn_files.csv` (since 2026-10-27) - array files that were
  stored and are no longer: one row per file with its parameters,
  MANIFEST status, SHA-256, source, stamp, constant rows, the date
  and the reason. The table rows they belonged to stay, with their
  size, hash and verification stamp. Three lines dated 2026-11-09
  are different: the Torres-Jimenez arrays CA(177; 4, 338, 2),
  CA(178; 4, 354, 2) and CA(179; 4, 358, 2) of the CAs data
  TJ2level_CAs were verified on 2026-08-23 but never stored (above
  the best known size at entry), and are listed so that the frame
  file's get none has the same reason as for the withdrawn files.
  Their status is the one such an array would have had
  (`above_best`), their constant rows were counted from the CAs
  data, and their reason says that they were never stored.
  `../tools/withdrawn_fingerprints.py` reads only the lines
  withdrawn on 2026-10-27 (the three files are in no commit;
  their fingerprints are in `tj_fingerprints.csv`). An array file is stored when it
  was built here, was submitted by its author, or comes from a
  public source whose author does not object to its redistribution.
  The author of the arrays of Torres-Jimenez's group in the CAs data
  objects TJ2level_CAs and CAEX_CAs objects to their redistribution,
  and his own repository is offline, so on 2026-10-27 the 137 of
  those files with no other public source were withdrawn (25 more
  are published in Dwyer's CA_Database and stay with it as their
  source). At 24 of those sizes the table holds arrays built
  here (S8) since 2026-10-27; one of them, CA(16; 4, 5, 2), is identical
  to the withdrawn file, so that array is still stored. At 40 more of
  those points S8 arrays were entered on 2026-10-28 (19 of his size, 21
  smaller, VERIFICATION_LOG.md).
- `certificates/` (since 2026-10-28) - certificates for arrays too
  large to store or to check in full: covering perfect hash families (CPHFs), from which
  `../tools/cphf/cphf_tools.c` rebuilds the array (the construction of
  Sherwood, Martirosyan and Colbourn 2006). `certificates/CERTIFICATES.csv`
  lists each file with its SHA-256, the SHA-256 of the array it expands
  to (the `array_sha256` of its table row) and the exact check that
  `../tools/cphf/repcheck.c` or `../tools/cphf/repcheck_pp.c` made of
  it, and since 2026-11-02 also its `family_sha256` (the SHA-256 of the
  family's canonical form `cphf1`) and its `expansion` (the rule that
  gives the array: `smc-1`, `smc-1-affine`, with `+fuse a>b` or
  `+fuse2 a` for a fused array; both defined in `../tools/cphf/README.md`).
  Certificates submitted since then are checked by
  `../tools/cphf/cphfcheck.c` (`../tools/check_certificates.py`), on
  GitHub in shards after the merge when the work fits the time budget of
  `../submissions/README.md`, and listed whether they entered as VERIFIED
  or as SCREENED. The first two were CA(40613; 5, 781, 5) and
  CA(218479; 5, 2801, 7), 63 MB and about 1.2 GB as text, whose
  families are 49 KB and 196 KB; `certificates/CERTIFICATES.csv` lists
  them all, and `../tools/cphf/README.md` says how to rebuild and
  recheck them.
- `withdrawn_fingerprints.csv` (since 2026-10-31) - for each of the
  137 array files withdrawn on 2026-10-27, its parameters and a
  fingerprint that does not change when rows or columns are reordered
  or symbols renamed (written by `../tools/withdrawn_fingerprints.py`
  from the repository history). The arrays themselves are not stored.
  The submission check uses it to flag a submission that is one of
  those arrays in disguise.
- `constructions/` (since 2026-11-02) - construction certificates: the recipe of an array built by
  a published construction (Power CZ, Colbourn and Zhou 2012; fusing a symbol and the derived
  array, Colbourn, Keri, Rivas Soriano and Schlage-Puchta 2010; the direct product of strength-2
  arrays), with its small ingredient arrays or the hashes of ingredient arrays of this table.
  `../tools/construction_cert.py` checks every hypothesis of the theorem exactly, rebuilds the
  array and prints its canonical sha256, in a fraction of a second; see
  `../tools/CONSTRUCTION_CERT.md`. The four certificates in `constructions/powercz/` prove arrays
  this project built, which are also stored in `arrays/` and verified by `ca_verify`. Since
  2026-11-02 a certificate is also a submission route (`constructions.csv`,
  `../submissions/README.md`). A certificate entered that way is stored in
  `constructions/<slug>/` with its ingredient files and listed in `constructions/CONSTRUCTIONS.csv`
  (file, t, v, k, N, construction, the certificate's sha256, array_sha256, the check, and the
  stored array, if any). Its row is VERIFIED, identified by the array_sha256 of the rebuilt array
  like every array row, with an empty family_sha256, and the array is stored in `arrays/` when it
  is at most 50 MiB as text. A larger one is kept only as its certificate, which rebuilds it.
  `../tools/consistency.py` rebuilds every listed certificate of at most 5 x 10^7 entries and
  compares the hash.
- `references.csv` (since 2026-10-31; ids since 2026-11-01) - the
  bibliography of construction methods: an `id` (for example
  `cphf-smc2006`), `keywords` (a case-insensitive regular expression
  for the usual names of the method, used to suggest ids), the full
  `reference` and its `doi` (or arXiv id). The `builds_on` column of
  the table lists these ids. Every DOI was checked against Crossref
  when it was added; the file grows as methods are added, never by
  guessing.
- `MANIFEST.csv` - one row per array file: parameters, status,
  SHA-256 of the canonical file content, retrieval recipe,
  verification stamp, and `constant_rows` (added 2026-10-20): the
  largest number of rows of the array that can be made constant by
  permuting symbols within columns, at most v. It is a property of
  the array that matters when the array is an ingredient of another
  construction. Computed by `../tools/constant_rows.c`, a standalone
  version of `cafast::maxconstant_c`, and checked against cafast on
  every array on file by `../tools/constant_rows_check.R`. The
  submission check computes it for every new array (empty, with the
  reason in the report, when the ten-minute budget is exceeded or the
  program could not be built). Whether an array splits into the
  blocks a product construction needs (its partition profile) is not
  computed; it is recorded only when the construction states it.
- `derived.csv` - generated, never edited by hand: sizes that follow from the
  counted rows by published constructions (fusing symbols, deriving a strength,
  adding one column (t >= 3), composition, Chateauneuf-Kreher doubling, CMTW Thm 3.4, k-ary Roux with Yin's
  DCAN values, Power CT, direct product, ordered design, Shokri-Moura), at the
  points where they are below the counted lookup. Its points are those of the
  counted lookup's grid and of up to four construction steps from it, so a longer
  add1 chain (up to eight steps), or a fuse step past the grid of its t and v,
  appears only in `ca_frame.csv`. One line per point with the
  construction and its arithmetic, every ingredient written CAN(t,k,v)=N.
  Recomputed from scratch by `../tools/derive_table.py` on every push to main and
  checked line by line by `../tools/consistency.py` without that program. These
  are computed sizes, not arrays: they are never part of the counted rows, and
  `best_derived()` in `ca_table.py` / `ca_table.R` is the lookup that includes
  them. The page lists them on `derived.html`. Past the baseline's column range
  (k = 20,000 at strength 2, 10,000 above) the constructions are also evaluated
  at a fixed ladder of widths up to k = 100,000, as a yardstick for arrays added
  there; where the table has no entry that wide, `lookup_N` and `gain_pct` are
  empty.
- `ca_frame.csv` - generated, never edited by hand: the best known sizes under the
  frame rule (`CONVENTIONS.md`, section 4), one line per stair step, described
  below under "The frame file". Rebuilt by `../tools/build_frame.py` on every push to
  main and compared with a fresh build by `../tools/consistency.py`.
- `above_rule_rows.csv` (since 2026-11-09) - edited by the maintainer: counted rows past the
  baseline's column range whose N is above a line of `derived.csv` at a width k' >= k, accepted
  knowingly (id, reason, decided_by, date). Such a row without a line here is reported as a
  warning by `../tools/consistency.py` on every run (`CONVENTIONS.md`, section 6, version 1.4).
- `ca_table.csv.gz` - `ca_table.csv` gzipped (about 300 KB instead of 2.8 MB), written
  by `../tools/build_frame.py` beside the frame file, without a file name or time in
  its header, so the same table always gives the same bytes. In R (read.csv cannot read
  a gzcon connection directly, so read the lines first):
  `read.csv(text = readLines(gzcon(url("https://raw.githubusercontent.com/chrispbsmolen/ca-tools/main/table/ca_table.csv.gz"))))`.
- `EXTERNAL.csv` - one row per array kept in a public deposit instead of
  `arrays/` (too large for the repository): its SHA-256, parameters, size in
  bytes, location (https URL, or zip URL `::` member), status and the stamp of
  the check by `tools/external_array.py`. Each has a VERIFIED or SCREENED row
  in `ca_table.csv` with the same hash. The status is `verified` exactly when
  a VERIFIED row has the hash, so an upgrade request that adds one (since
  2026-11-02) also sets the status to `verified` and the stamp to that of
  the exact check.
- `VERIFICATION_LOG.md` - the record of the verification runs that
  produced the stamps.
- `verify_pipeline.R` - the canonicalization, hashing, and
  verification code used to stamp rows, so anyone can stamp new ones
  the same way.

Some arrays contain `NA` don't-care entries. Verification uses the
"promise" semantics: coverage holds on the concrete entries alone, so
these arrays remain covering no matter how the don't-cares are filled.

The `exceeds_snapshot` arrays (their number is in the counts above)
are of two kinds. Most are other people's work: arrays built by the
CAs package's implementations of published constructions, an array
from Aaron Dwyer's CA_Database, the 23 arrays of Mickael Bergeron's
submission, and three arrays built here from Theorems 5.1 and 6.2 of
Shokri, Moura and Stevens (arXiv:2510.13122). Their run sizes beat the
November 2024 snapshot's recorded rung at their parameters. Those
improvements belong to their sources, and this table's contribution is
only the verification stamp and the side-by-side accounting. The others
are S8 arrays of this project: seven at sizes that Torres-Jimenez's
arrays reached first (three entered 2026-10-27 and four 2026-10-28),
CA(2663; 5, 121, 3), from a cyclic covering perfect hash family
(`../tools/cphf/`), and 23 arrays of 2026-10-28 and 2026-10-29 that are also smaller
than every array the table held at their points, the arrays of
Torres-Jimenez's group included: 20 binary strength-4 arrays with 148
to 324 columns, 1 to 4 rows below his (row elimination and tabu search
from Paley arrays), and CA(401; 6, 27, 2), CA(411; 6, 28, 2) and
CA(420; 6, 29, 2), 3, 4 and 1 rows below (from the CA(440; 6, 30, 2) of
Wagner, Kampel and Simos). Two more S8 rows below the
snapshot, CA(40613; 5, 781, 5) and CA(218479; 5, 2801, 7), are given by
certificates and have no array file; they reach more columns at sizes
that Torres-Jimenez and Izquierdo-Marquez reached first (40613 at
k = 500 in the snapshot, 218479 at k = 1600 in their 2024 paper). Each such row's notes name the snapshot value it
beats.

## Schema

`t, v, k, N` is the claim, with stair-step semantics: the row means
"N runs suffice for a strength-t covering array on up to k columns of
v symbols". `tier` is the evidence class:

- `CITED` - traceable to a dated snapshot or publication, no array in
  hand. The 13,641 baseline rows are the November 2024 status of the
  Colbourn tables, taken from the `colbournBigFrame` snapshot that
  Ulrike Groemping preserved in her CAs package after the original
  site (public.asu.edu/~ccolbou) became unavailable (source S1). Since
  2026-10-25 a size published in a paper is also entered as a CITED
  row while no array is in hand (source S7): `snapshot_id` is the DOI
  or arXiv id, `source_detail` names the table or theorem, the notes
  credit the paper and give the snapshot value it beats, the
  construction is described in the paper's terms, and the array fields
  are empty. The first are the 152 order-seven sizes of Torres-Jimenez
  and Izquierdo-Marquez (Mathematics 12 (2024) 1908), which the
  snapshot does not include; `../tools/add_tjim7.py` writes them from
  `../tools/tjim7_order_seven.csv`. On 2026-11-09 `../tools/add_sms_cited.py`
  added 19 more, each N computed there from the theorem's formula. Nine are
  strength-4 sizes of Shokri, Moura and Stevens (arXiv:2510.13122v3, Theorem 5.1
  and Corollary 6.5, q = 13, 17, 19, 23 and 25). The q = 13 row is their own 133874, above the
  verified 133873 made from it, so it is not the best known. Ten are strength-3
  sizes of Shokri and Moura (J. Combin. Des. 33 (2025) 156-171), read in Chapter
  5 of Shokri's open thesis, so their theorem numbers are thesis numbers. Two of
  them (q = 23 and 25, k above 10,000) are formula values past the paper's
  table. Because these cited sizes are smaller, 10 frame steps covering 23,610
  widths (t = 3 and 4, v = 20 to 25) now have a CITED best value with no array
  (get none) where they had a VERIFIED one. The verified steps are still in the
  frame at the next wider k. Such a row counts as best known like any
  CITED row; a verified array can be added beside it later.
- `VERIFIED` - an explicit array is in hand and was checked
  exhaustively at the claimed strength, by the caverify kernel or, for
  community submissions, by `ca_verify.c` at a fixed commit. The row
  carries the array's SHA-256 (canonical form) and a stamp naming the
  verifier and its version or commit, the date, and the machine. Since
  2026-10-28 an array too large to check that way may instead be given
  by a covering perfect hash family with a cyclic symmetry, stored in
  `certificates/` and checked exactly by `../tools/cphf/repcheck.c` or
  `../tools/cphf/repcheck_pp.c` (any t, prime-power q): the
  symmetry of every row is checked, not assumed, and then every set of
  t columns that contains the first column is checked, which covers all
  sets of t columns. The array follows from the family by the theorem
  of Sherwood, Martirosyan and Colbourn (2006). Such a row's stamp names
  `repcheck` or `repcheck_pp` and the first twelve hex digits of its source's SHA-256,
  and its `array_sha256` is the hash of the array rebuilt from the
  family. Since 2026-10-31 such an array may also have symbols fused
  (one symbol written as another), which keeps every tuple covered by
  Lemma 3.1 of Colbourn, Keri, Rivas Soriano and Schlage-Puchta (2010);
  the stamp then says "fused", the certificate is listed again in
  `certificates/CERTIFICATES.csv` for the fused array, and the fused
  array is spot-checked directly as well. Only fusing, and only from
  certificates this table has checked itself, is accepted this way.
  Since 2026-11-02 a submitted certificate is checked by
  `../tools/cphf/cphfcheck.c` with the cheapest exact method it finds in
  the data (a certified cyclic symmetry, progression rows, projection
  hashing or every set of t columns), on GitHub in shards when the work
  fits the time budget (`../submissions/README.md`, "Certificates"); its
  stamp begins `cphfcheck` and ends "(CPHF certificate, exact)", or
  "(CPHF certificate, exact; array not hashed)" for an array of more than
  10^12 entries, whose `array_sha256` is then empty and whose
  `family_sha256` identifies it.
  Since 2026-11-02 an array may also be given by a construction
  certificate (`constructions/`, above), checked by
  `../tools/construction_cert.py`; its stamp is
  `construction_cert <tool> <date> <machine> (<construction>, exact)`,
  the tool being the first twelve hex digits of the sha256 of that
  program.
  Every VERIFIED row therefore has a check method, read from its stamp
  by `check_method()` in `ca_table.py`: "direct" (the array itself
  checked exhaustively), "certificate", "certificate + fusing", or
  "construction certificate". The
  page shows it with each row, and the lookups can be limited to the
  methods a reader trusts (`counted(rows, methods=...)`,
  `counted_rows(tab, methods = ...)` in R; the default counts all).
- `FAILED_PENDING_RECHECK` - a verification attempt that failed its
  dimension check. Kept because history is never rewritten; each such
  row is superseded by a later resolution row. The three present at
  publication share one cause, per U. Groemping: the Dwyer
  CA_Database holds two arrays for some parameter sets and dwyerCA
  always fetches the smaller, so walking the catalogue trips the
  dimension check on the larger twins (VERIFICATION_LOG.md has the
  three pairs). All three arrays verify at their actual sizes.
- `SCREENED` - an array too large for the public check, screened on
  random column windows instead of verified in full (see
  `../submissions/README.md`). Listed but not counted as best known;
  when the array is later verified in full it gets a new VERIFIED row
  (below), entered by the maintainer, since the submission check
  rejects an array whose hash is already in the table.
  Since 2026-11-02 also a covering perfect hash family whose
  exact check is over the time budget of the public runners: screened on
  random column windows of the family and random sets of t columns, its
  stamp ends "(CPHF certificate, screened)", and an exact check run later
  on any machine (`python3 tools/check_certificates.py ... --apply`) adds
  the VERIFIED row beside it (the maintainer commits it, since a pull
  request may only add files under `submissions/<slug>/`).
  Since 2026-11-02 anyone can ask for the exact check of SCREENED
  entries with a request, `submissions/<slug>/upgrade.csv`
  (`../submissions/README.md`, "Upgrading a SCREENED entry"). It runs on
  GitHub after the merge (`../tools/check_upgrades.py`, `ca_verify` in
  shards for an array, `cphfcheck` in shards for a family) within the time
  budget of certificates, and each entry that passes gets a VERIFIED row
  with the same t, v, k, N, `source_id`, `source_detail`, `snapshot_id`,
  `array_sha256` and `family_sha256`, the same `construction` and
  `builds_on`, notes that keep the original credit and say "exact check
  of the SCREENED row of DATE, requested in submissions/SLUG by CREDIT",
  and the stamp of the exact check (`ca_verify <commit> <date>
  github-actions`, with "(exact, M shards)" when it was split, or
  `cphfcheck ... (CPHF certificate, exact)`). `../tools/consistency.py`
  requires such a row to match exactly one SCREENED row of that date and
  to be the only VERIFIED row of its array.
- `DISPUTED` (defined 2026-10-23; until then reserved, with no rows) -
  a CITED entry whose cited construction, as implemented and checked
  here, did not give a covering array at the recorded size. It is
  recorded as an added row
  with the same t, v, k and N; the CITED row stays unchanged and is
  still counted by the lookups below. The DISPUTED row's notes say what
  failed and how it was checked, and its `source_detail` gives the
  recipe that was checked. It does not say that the size cannot be
  reached. The first three, entered 2026-10-23, are the cyclotomy
  entries CAN(3, 128, 6), CAN(3, 2162, 20) and CAN(3, 2312, 21)
  (VERIFICATION_LOG.md).
- `RETRACTED` (defined 2026-10-31) - a VERIFIED or SCREENED row found
  wrong after it was entered, for example an array a later check shows
  is not covering, or a stamp from a faulty verifier build. It is
  recorded as an added row with the same t, v, k, N, `array_sha256`
  and `family_sha256` as the row it retracts, and notes saying what was
  found and how. The
  retracted row stays in the file, unchanged, but no longer counts as
  best known, so the lookups below drop it at once. Anyone can raise a
  suspected error by opening an issue with a check that fails;
  `../tools/consistency.py` requires that a RETRACTED row matches
  at least one VERIFIED or SCREENED row (it retracts every row with that
  key: a row upgraded from SCREENED has its SCREENED twin) and has notes.
  A pull request that adds one changes the counted rows, so it also
  regenerates `derived.csv` (`python3 tools/derive_table.py`, a few
  minutes) and `ca_frame.csv` (`python3 tools/build_frame.py`):
  `consistency.py --pr` checks both against the rows.

`family_sha256` (added 2026-11-02, the last column) is empty except in
rows given by a covering perfect hash family checked by `cphfcheck`: the
SHA-256 of the family's canonical form `cphf1` (first line
`cphf1 n k q t`, then n lines of k decimal codes, single spaces, a line
feed after every line, rows and columns as given;
`../tools/cphf/README.md`). Every certificate row entered since then has
it. A row's array is identified by `array_sha256` whenever the array has
at most 10^12 entries (N times k); above that a certificate row may leave
`array_sha256` empty and is identified by `family_sha256`, which
`certificates/CERTIFICATES.csv` must list. `identity()` in `ca_table.py`
and `row_identity()` in `ca_table.R` give either, and the page shows
such a row as "identity: family ... (array not hashed)". The ten
certificate rows entered before the column existed (stamps `repcheck`
and `repcheck_pp`) had it filled once, with the family_sha256 of their
listing in `certificates/CERTIFICATES.csv` (below, "How to append a
row"); the row of CA(2663; 5, 121, 3), whose array is stored and was
checked directly by `ca_verify`, keeps it empty.

`source_id` names the source class (S1 Colbourn snapshot, S4 NIST
covering array library, S5 Dwyer CA_Database, S6 the CAs package's
data and constructions, S7 literature and community submissions). `source_detail` is the exact
retrieval or generation recipe. `snapshot_id` dates the source.
`lb, lb_evidence` are reserved for lower-bound evidence and are empty
in this version. `construction` (added 2026-10-20) names the
construction or search that produced the entry, in the words a
covering array researcher would use. For the CITED baseline rows it
is Colbourn's own construction label, the same text as their
`source_detail`. For arrays entered through the submission check it
is the submitter's `construction` field, which the check requires.
For the 530 verified rows that entered from the NIST library, the
Dwyer database and the CAs package before the column existed, it was
filled on 2026-10-20 from the catalogues that describe those sources
(NIST ipof directory, `CAs::DWYERcat$Source` with Dwyer's own method
code quoted verbatim, `CAs::TJcat`, `CAs::CAEX_CAs`, and the KSK call
itself), by `tools/backfill_construction.R` and
`tools/apply_construction_backfill.py`; the mapping with its basis
per row is `construction_backfill.csv`. Nothing was inferred: a value
names the catalogue entry it was read from, and the Torres-Jimenez
arrays say that the method is not recorded per array.
`builds_on` (added 2026-11-01) lists the published work the entry's
construction rests on, as ids of `references.csv` separated by
semicolons, and `new` followed by a link for a method of the
submitter's own (see `../submissions/README.md`). A submission must
give it, and the check validates it. For the rows that predate it,
it was filled by `../tools/backfill_builds_on.py` from the ids whose
keywords match the row's `construction` (for the baseline, Colbourn's
label), with the Dwyer method codes and Bai XunDi's deposited
construction mapped by hand as that script lists. A row whose
construction names no traceable source is left empty rather than
guessed: on 2026-11-01 that was 1,525 of the 13,641 baseline rows
(mostly "Add factors", the bare perfect hash family labels and the
Torres-Jimenez simulated annealing entries) and 305 others. The
table page lists every cited work at its foot. The notes of a submission row
say "exceeds table: previous best N (row k=..., source)" (or "equals
table: ...") once; that is the comparison the check made at entry, and
it is not repeated. Comparisons in notes hold as of entry: "equals
best known" in the older rows means that N equalled the November 2024
snapshot's best known size at those parameters when the row was
entered, and the MANIFEST status `equals_best` means equal at entry
(to the snapshot for those rows, to the table's best for a file from
the submission check); a new hand-entered row that ties says "equals
snapshot rung (snapshot best N at this k)" instead. The current best
known size is what the lookups below return. Every construction
belongs to the sources the row names. A row whose construction is this
project's own says "this project's construction" in its notes (the S8
rows, since 2026-10-27, except CA(32; 4, 13, 2), whose ingredient is
credited to Colbourn, Keri, Rivas Soriano and Schlage-Puchta 2010;
CA(79; 5, 15, 2) of 2026-10-28 and CA(401; 6, 27, 2), CA(411; 6, 28, 2)
and CA(420; 6, 29, 2) of 2026-10-29 say it and also credit their
starting arrays, by the same authors and by Wagner, Kampel and Simos
2021).
Some rows entered up to 2026-10-25 say in their notes that the
improvement or construction is not this project's; later rows leave
that to this paragraph.

## Reading the table from code

The CSV at
https://raw.githubusercontent.com/chrispbsmolen/ca-tools/main/table/ca_table.csv
is the whole table, always current, and the only interface. There is
no separate API. The rows that count as best known are the rows of
tier CITED or VERIFIED, less any VERIFIED row that a RETRACTED row
names (same t, v, k, N, `array_sha256` and `family_sha256`). This is defined once, by
`counted()` in `ca_table.py`, which the tools in `../tools/` import,
and mirrored by `counted_rows()` in `ca_table.R`. The stair-step rule
gives the best known N at (t, v, k) as the smallest N among the
counted rows with the same t and v and k at least the requested k.

The counted lookup uses only rows entered at the same number of
symbols v, so that each counted entry points to an array, or a cited
size, of exactly that kind. An array over more symbols also gives
sizes at fewer symbols, for example by fusing (Colbourn, Keri, Rivas
Soriano and Schlage-Puchta 2010, Lemma 3.1: CAN(t, k, v) <= CAN(t, k,
v + m) - 2m). Such reductions are computed sizes, not arrays. They are
listed in `derived.csv` and returned by `best_derived()`, and never
mixed into the counted lookup (raised in issue #30). The frame file
below counts the ones made by a proven rule, on lines of their own.

### The frame file (ca_frame.csv)

`ca_frame.csv` is the one file to read for "what is best here, how is it
made, and how do I get it". It counts what the counted lookup counts plus
proven derived sizes: fuse (Colbourn, Keri, Rivas Soriano and Schlage-Puchta
2010, Lemma 3.1), derive (same paper, (7)) and add1 (same paper, Theorem 3.2:
CAN(t, k, v) <= CAN(t, k-1, v) + v(v-1) CAN(t-2, k-2, v), one added column,
Colbourn's label "Add 1 factors"; all 133 of his rows with that label follow
from his own rows by it), applied again and again to the counted rows until
nothing changes. add1 is used for t >= 3. Its second input, the strength t-2
ingredient, is for t >= 4 a row (or a row fused or derived; never a size itself
made by add1), and for t = 3 the trivial strength 1 array CA(v; 1, k-2, v), the v
constant rows, so a step at t = 3 adds v(v-1)v rows and names no ingredient. The
construction is valid for every t >= 2: copy column k-1 into a new column k;
a t-set of columns without the new column, or with it but without its copy, is
covered by the old array; one with both is covered by the old array where the two
symbols agree and, for each ordered pair (x, y) of distinct symbols, by the
strength t-2 array appended with x and y in the two columns (it was also checked
on 31 arrays built from arrays on file at t = 2 and 3, and 21 at t = 4 to 6, each
verified exhaustively). Among ingredients of the same size a VERIFIED row is
named before a CITED one, so a step is CITED only when it cannot be helped. No derived size is built from the three CITED cyclotomy
rows that have DISPUTED rows beside them. A derived size sits at the width of its
source row, less one per derive step and plus one per add1 step (a working may
pass through a point past the counted range on its way, but is written only at
its last point), so past the
baseline's column range there are derived sizes only near the rows entered there
(for example the fused sizes of the width 100,000 arrays), and no ladder of
widths. Past every counted row of its t and v, a derived size counts only when it
is made by fuse alone: derive there gives sizes far above known values (252 at
t = 2, v = 2, k = 99,999, where 21 is exact), and derived points beyond the
counted range, by derive or add1, are left for later (`CONVENTIONS.md`, section 6).
A fused size there counts only if no line of `derived.csv` at the same t and v and
a width k' >= k, by any size rule counted or not, has a smaller N (version 1.3,
issue #62), so the fused sizes at t = 3 with 2 and 3 symbols past 10,000 columns
are withheld. A row past the baseline's column range that `derived.csv` beats at
its own width counts, but does not widen the counted range (version 1.4); such
rows accepted knowingly are listed in `above_rule_rows.csv`.
add1 is in the working of many steps of the frame (how many, and how many at
t = 3, is in the generated counts at the top). At t = 3 each is one step from a
covering perfect hash family row, for example
CA(832; 3, 15180, 4), `Sherwood covering perfect hash family (affine):add1`,
from CA(784; 3, 15179, 4). At higher strengths a step can go below Colbourn's own
"Add 1 factors" size, for example CA(4257520; 6, 238, 8),
`SCPHF Random Extension (CLS):add1`, below his 4259480 there, because its
strength 4 ingredient is now a smaller row (`t4-v8-k274-2`).

There is one line per stair step, in the sense of the page: for each t and v, a
step (k, N) has N smallest at every k' >= k and k the largest width with that N.
Every line is CITED or VERIFIED, so no tier filter is needed. The columns are
those of `CONVENTIONS.md`, section 7. t, v, k, N and construction keep the
meaning they have in `ca_table.csv`. basis is row when a counted row reaches N
there (that row is named, with its id), and derived otherwise. A derived line has
no id, get none, the tier of its weakest row (CITED when its source row or an add1
ingredient row is CITED), the latest entry date of those rows, and as construction
its working: the source row's own construction label followed by one `:fuse`,
`:derive` or `:add1` per step, in the order applied (for example
`Sherwood covering perfect hash family (affine):fuse:fuse`). This is close to the
form CAs shows in its Source column, but not the same: CAs 0.25 writes a run of
`:fuse` or of `:add1`, never both, and `:derive` last, while here some
workings mix them (how many is in the generated counts at the top) (`:fuse:add1`, `:derive:fuse`, `:derive:fuse:add1`), so read
the steps with the split below, not with CAs's own label parser. CA(5289; 3, 629, 10), from the VERIFIED CA(5291; 3, 629,
11), reads `Sherwood covering perfect hash family (affine):fuse`. The source row's
id (here `t3-v11-k629-1`) is in ids_all, so the author stays traceable, and
constructions_all lists every working in the same label form. An add1 step at t >= 4 has two
inputs: its ingredient row's id follows the source row's id in ids_all after a `+`,
one per add1 step at t >= 4 in order (for the example above
`t6-v8-k237-1+t4-v8-k274-2`); the ingredient's own fuse or derive steps are not
written. An add1 step at t = 3 names no ingredient (its ingredient is the trivial
array above). A label may contain
commas and colons: the file quotes such fields as CSV does, so `read.csv` reads
them whole. To split a working into label and steps, remove the trailing `:fuse`,
`:derive` and `:add1` pieces; no source label ends in one (a row whose label is
empty, ends in one of them or contains " || " is written by its id instead, in
construction of a derived line and in constructions_all; `../tools/consistency.py`
checks this, that there are exactly v of the source - v fuse steps, t of the
source - t derive steps and k - k of the source + t of the source - t add1 steps,
and that the steps applied to the named rows give N). In R:

    m <- regmatches(w, regexpr("(:(fuse|derive|add1))+$", w))
    label <- substr(w, 1, nchar(w) - nchar(m)); steps <- strsplit(sub("^:", "", m), ":")[[1]]

get and get_ref say
where the named row's array is (file, deposit, certificate, construction, cas,
url, none) and give its path, link, URL, R call or rebuild command. When the
named row has none (a CITED row is named first among ties) but another counted
VERIFIED row tied at the same step has an array, get and get_ref are those of the
first such row in the tie order below; id, tier and construction stay those of the
named row, and the row lending the array is in ids_all. A
certificate's rebuild command runs the program cphfcheck from the repository
root, which is shipped as C source: build it first with
`gcc -O3 -fopenmp -o tools/cphf/cphfcheck tools/cphf/cphfcheck.c` (on macOS,
clang with libomp, as in `../tools/cphf/README.md`).
constructions_all and ids_all list every counted row (or, on a derived line,
every working) that reaches N, separated by " || " and ";" (with "+" inside an
ids_all entry before each add1 ingredient). Ties are named in the
order of `CONVENTIONS.md`, section 9: a CITED row first, then more constant rows
(an unknown count, an empty constant_rows, ranks below every known count, so a
row with a counted array is named before an equal row whose array was never
counted, even an earlier one), the earlier entry date, the wider array, the id.
get is none on every derived line, and on a row line when neither the named row
nor a counted VERIFIED row tied at its step has an array the table can point to.
So most CITED lines have get none, and a CITED line has an array (get file, for
example) when a VERIFIED row ties it; a VERIFIED line has get none when its array
is not stored, such as the withdrawn files of the CAs data (`TJ2level_CAs`,
`CAEX_CAs`). The generated counts at the top give both numbers. The tier of a
derived line is that of its weakest input row: VERIFIED there means that every
input row is VERIFIED, not that the derived array itself was built or checked
(it was not, and its get is none).
family is empty on every line for now, so `read.csv` reads it as logical NA;
test it with `is.na(fr$family) | fr$family == ""`.

Ids are t<t>-v<v>-k<k>-<n>, n the row's number at its point (t, v, k) in file
order, so they never change as rows are appended. They are computed by
`../tools/build_frame.py`, not stored in `ca_table.csv` (yet).

prev_id is the previous best at the step. On a row line, take the first row in
file order that reaches N or less at k' >= k, counting the rows of one snapshot
entered on one day as one entry (so the 13,641 baseline rows have no order among
them). prev_id is the named row of the best value over the counted rows entered
before it, at k' >= k, and is empty when there is none, as on every step set by
the baseline. On a derived line, prev_id is the named row of the counted lookup
at the step, the value it improves on. Past every counted row of its t and v it
names the row at the widest counted width when the step's N is below that row's
(for example CA(13115; 3, 11288, 12) and the 13,151 at k = 10,000), and is
otherwise empty.
prev_id names rows only. generated is the latest entry date in `ca_table.csv`, so
rebuilding an unchanged table gives the same file.

In R, the eCAN-style lookup over the frame file:

    fr <- read.csv("https://raw.githubusercontent.com/chrispbsmolen/ca-tools/main/table/ca_frame.csv",
                   stringsAsFactors = FALSE)
    eCAN_frame <- function(fr, t, k, v) {
        s <- fr[fr$t == t & fr$v == v & fr$k >= k, ]
        if (nrow(s) == 0) return(data.frame(CAN = NA, Source = ""))
        i <- which.min(s$N)
        data.frame(CAN = s$N[i], Source = s$construction[i])
    }

In R, with no packages:

    tab <- read.csv("https://raw.githubusercontent.com/chrispbsmolen/ca-tools/main/table/ca_table.csv",
                    stringsAsFactors = FALSE,
                    colClasses = c(array_sha256 = "character", family_sha256 = "character"))
    tab$N <- as.numeric(tab$N)
    counted_rows <- function(tab) {
        key <- function(x) paste(x$t, x$v, x$k, x$N, x$array_sha256, x$family_sha256)
        r <- tab[tab$tier == "RETRACTED", ]
        tab[tab$tier %in% c("CITED", "VERIFIED") &
            !(tab$tier == "VERIFIED" & key(tab) %in% key(r)), ]
    }
    best_known <- function(tab, t, v, k) {
        s <- counted_rows(tab)
        s <- s[s$t == t & s$v == v & s$k >= k, ]
        if (nrow(s) == 0) NA_real_ else min(s$N)
    }
    best_known(tab, 3, 13, 197)   # 6422 as of 2026-10-18 (Bergeron)

`ca_table.R` in this directory has `load_ca_table()` and the same
`best_known()`, and `ca_table.rda` is the table as an R data frame.
SCREENED rows are listed but excluded from best known on purpose. When
a screened array is later verified in full, it gets a new VERIFIED row
with that machine's stamp, the SCREENED row stays in the file, and the
page no longer shows it. Bergeron's three v = 19 arrays went this way
on 2026-10-21, from full checks run on 2026-10-18. The file grows by
one row per accepted claim.

DISPUTED rows (since 2026-10-23) are listed and not counted, and the
CITED row a DISPUTED row disputes is still counted, so the lookups
above give the same values as before the DISPUTED rows were added. To
leave the disputed CITED values out as well, filter them first and use
`tab2` in place of `tab`:

    d <- tab[tab$tier == "DISPUTED", ]
    tab2 <- tab[!(tab$tier == "CITED" & paste(tab$t, tab$v, tab$k, tab$N) %in%
                  paste(d$t, d$v, d$k, d$N)), ]
    best_known(tab2, 3, 6, 128)   # 768, where best_known(tab, 3, 6, 128) is 762

### In place of the frozen Colbourn tables (eCAN, eCAK)

`CAs::eCAN(t, k, v)` and `CAs::eCAK(t, N, v)` read the frozen
Colbourn tables in `CAs::colbournBigFrame` and return the best N for
at least k columns, or the most columns for at most N runs, with that
row's Source text. This table can stand in for them.
`tools/ecan_compare.R` checks it. Its output with CAs 0.24-4 (it has not been run
again with CAs 0.25, on CRAN since 2026-11-07) is
kept in `../results/`, one file per run, the latest
`ecan_compare_2026-10-25.txt`. The 13,641
baseline rows (CITED, source S1) equal `colbournBigFrame` row for row,
with `construction` equal to its `Source`. The lookups below, run over
the baseline rows alone, reproduce eCAN and eCAK exactly, number and
Source text, at every one of the 13,641 points of the frozen tables.
Run over all CITED and VERIFIED rows together, they give a smaller N at some of
those points and more columns at others, and never a worse value;
the current numbers are in the generated counts at the top, computed
the same way. In R,
with `tab` read as above:

    eCAN_table <- function(tab, t, k, v) {
        s <- counted_rows(tab)
        s <- s[s$t == t & s$v == v & s$k >= k, ]
        if (nrow(s) == 0) return(data.frame(CAN = NA, Source = ""))
        i <- which.min(s$N)
        data.frame(CAN = s$N[i], Source = s$construction[i])
    }
    eCAK_table <- function(tab, t, N, v) {
        s <- counted_rows(tab)
        s <- s[s$t == t & s$v == v & s$N <= N, ]
        if (nrow(s) == 0) return(data.frame(CAK = NA, Source = ""))
        i <- which.max(s$k)
        data.frame(CAK = s$k[i], Source = s$construction[i])
    }

The functions count exactly the rows `counted_rows()` returns. If
another tier is added to the table later, it is documented here, and
these lookups keep their meaning until a caller chooses to count it.

The address above always serves the newest table, so the same call
can return a smaller N next month. For a result that can be repeated,
read the table at a fixed commit, for example

    https://raw.githubusercontent.com/chrispbsmolen/ca-tools/9494361e011d3b96645164032c3abe4fa7537c09/table/ca_table.csv

and report the commit with the result. The table is append-only in
its claims, so a fixed commit always reads the same. The newest
commit is listed at
https://api.github.com/repos/chrispbsmolen/ca-tools/commits/main
(field `sha`). For use without a network, `ca_table.rda` holds the
same table as an R data frame, small enough to travel inside a
package, refreshed at each release.

## How to append a row (maintainer's guide)

The table is append-only in its claims: a row's t, v, k, N, tier,
source_id, source_detail, snapshot_id, array_sha256, verify_stamp,
entered and (since 2026-11-02) family_sha256 are never changed, and a better N
or a correction is a new row. Since 2026-10-31
`../tools/consistency.py --base` enforces this on every pull request
and every push to main (the free-text columns notes, lb, lb_evidence
construction and builds_on may still be corrected in place). The one
exception is family_sha256 going from empty to a value, allowed only in
a VERIFIED or SCREENED row checked through a certificate (stamp
`repcheck`, `repcheck_pp` or `cphfcheck`) and only to the family_sha256
of that row's listing in `certificates/CERTIFICATES.csv` (same t, v, k,
N and array_sha256); once set it never changes. The things written
into existing rows since publication are all recorded here (dates as in the
commits, US Central time): on 2026-10-19 the new `construction` column
was filled for rows that predate it (above; commits a1ad327 and
597a5f7), and the notes of the 23 Bergeron rows lost a fragment that
repeated the previous best (a1ad327); the same evening the
`construction` text of the 23 Bergeron rows was corrected to the
formula checked against all 23 arrays (80791b8); on 2026-10-20 the
`construction` text of the three Dwyer resolution rows was corrected
(50b439f); on 2026-10-21 the `construction` text of the 24 CAEX rows
was made precise, in two passes (90539cf, 1bc0699): their last step is
column extension by computer search, per the `CAs::CAEX` help page, not
a product construction, which CAEX uses only for N = 34 and 36 to 50;
on 2026-10-23 the notes of the three Dwyer resolution rows were
corrected (the guess that the repository file had been improved in
place is superseded by VERIFICATION_LOG.md: the database holds twin
arrays), and the notes of the three SCREENED Bergeron rows were made
consistent (they were screened on the public runner, and the full check
on the maintainer's machine is recorded in the VERIFIED rows with the
same hash); on 2026-10-25 the notes of four rows were replaced by notes naming
their sources and ingredients (the 2215, 3381 and 9330 rows of
2026-10-21, and the CA(15; 3, 12, 2) row of 2026-08-23, whose array
is the one Nurmela printed in 2004 with the two symbols exchanged and
two rows moved); on 2026-10-27 the notes of the 137 rows whose array
files were withdrawn (`withdrawn_files.csv`) were extended by a
sentence saying so (for CA(16; 4, 5, 2), that the identical array is
stored as built here); on 2026-11-01 the new `builds_on` column was
filled for every row that predates it (above); on 2026-11-02 the column
`family_sha256` was added at the end of every row, empty in all existing
rows (the append-only check reads it as empty in older versions of the
table), and in the same change it was filled, once, in the ten
certificate rows that predate it (CA(40613; 5, 781, 5), CA(218479; 5,
2801, 7), CA(10921; 6, 121, 3), CA(249985; 6, 781, 5), CA(49985; 5,
1562, 5), CA(767625; 5, 1210, 9), CA(268897; 5, 5602, 7), CA(885721;
5, 7381, 9) and the two fused arrays CA(249985; 6, 781, 4) and
CA(249983; 6, 781, 4)), with the family_sha256 of their listings in
`certificates/CERTIFICATES.csv` (computed from the stored families, as
the column `family_sha256` of that file was). To add a claim with evidence:

1. Get the array (download, construct, or receive it) and note the
   exact recipe: URL and date, or the generating call and package
   version, or the DOI.
2. Canonicalize: 0-based integer symbols, one run per line, space
   separated, newline endings. `verify_pipeline.R::canon_serialize`
   does this; `canon_sha256` hashes it.
3. Verify: `verify_claim(D, t, v, k, N, source_id, source_detail)`
   runs caverify at strength t and returns an append-ready row with
   the hash and stamp filled in. A failed check returns a
   FAILED_PENDING_RECHECK row; recheck from a fresh copy before
   concluding anything, catalogues go stale (see the log).
4. Append the row to `ca_table.csv`; never change the fields named
   above in an existing row. A
   better N is a new row; a correction is a new row whose notes
   reference what it supersedes.
5. If you add the array to `arrays/`, add its MANIFEST.csv line.
   After the push, the table-page workflow regenerates `ca_table.rda`
   and the generated counts, rebuilds the page and runs
   `tools/consistency.py --check` and the self-test; a failure turns
   the run red and GitHub sends an email.

Since 2026-10-18 the usual route is the submission check
(`../submissions/README.md`), which does steps 2 and 3 on a pull
request and step 4 after the merge (`table-page.yml` on main), and fills
`construction` and `builds_on` from the claim.

### Admissible sources

Every row comes from a source that can be dated and fetched again or
derived again. The source classes are:

- S1, Colbourn's tables as preserved in `CAs::colbournBigFrame` (CAs
  0.24, snapshot `colbourn-2024-11-ug`), the baseline.
- S2, Ulrike Groemping's HTML mirror of the same tables, used only to
  cross-check S1. No rows.
- S3, Internet Archive captures of the original tables, each cited by
  its capture URL and date, used only to compare the tables' history.
  No rows.
- S4, the NIST covering array library, explicit arrays cited by exact
  URL.
- S5, the Dwyer CA_Database, explicit arrays cited by commit and path.
- S6, data and constructions of the CAs package, cited by package
  version and generating call.
- S7, the literature, cited by DOI or arXiv id: a peer-reviewed
  paper, a preprint with a stable identifier such as an arXiv id, or a
  thesis. A self-published deposit (for example a personal Zenodo
  record) is not citable by itself: sizes from it enter only as arrays
  through the submission check. When a later version of a paper
  changes a value, a new row cites it and the old row stays (CITED, or VERIFIED
  when the paper or its supplement provides the array or, since
  2026-10-25, when the array is built here from the paper's
  construction by a script in `../tools/`), and community submissions,
  explicit arrays verified by the submission check.
- S8 (since 2026-10-27), arrays built by this project with its own
  scripts in `../tools/own_arrays/` and, since 2026-10-28,
  `../tools/cphf/` (searches, algebraic constructions and
  post-optimization written here), verified in full or, for an array
  too large to store or to check in full, through its certificate (`VERIFIED` above); the row names
  the script and the method, and its notes say "this project's
  construction" (all but CA(32; 4, 13, 2), whose notes credit its

## Correcting credit

The claim of a row (t, v, k, N, tier, source, hash, stamp, dates) never changes; a
wrong result is withdrawn by a RETRACTED row. Credit can be wrong too: a missing
reference in builds_on, a starting array whose author is not named, a 'new'
method that is someone else's. The three credit fields of a row (notes,
construction, builds_on) are corrected in place with `../tools/correct_credit.py`,
which edits the one line of the row and appends a line to `CREDIT_CORRECTIONS.csv`:
the date, the row, the field, the old and new value, the reason, and who asked.
`../tools/consistency.py --check` requires every logged correction to match the
table, and with `--base` it refuses a change to a credit field of an existing row
that has no line in the log, so no credit changes silently. On the page a
corrected row is marked "credit corrected <date>", linked to the log.

    python3 tools/correct_credit.py --row 3,12,196,6228 --field builds_on \
        --add postop-nck2013 --reason "..." --requested-by "..."        # dry run
    ... --apply                                                          # write
