# Benchmarks: ca_verify2 against ca_verify

Since 2026-11-02 the program called ca_verify2 here is `ca_verify.c` itself (version 2), and
the program called ca_verify here is the first version, which it replaced. The names below are
those of the time of writing.

Machine: this VM, 2 vCPUs of an Intel Xeon at 2.1 GHz (AVX2 and AVX-512
present; ca_verify2 uses its AVX2 kernel), 8 GB RAM, gcc 13.3, both tools
built with `cc -O3 -pthread`. During all measurements the main session's
own `ca_verify` run on CA_216_4_1368_2 (two threads, started 21:28 UTC) was
occupying one core, and other sessions' tests were running intermittently,
so wall-clock times are not meaningful here. All numbers below are CPU
seconds (user + sys) of the process, which is what both tools' work
amounts to; on an idle machine wall time is CPU time divided by the number
of threads, see "Scaling" at the end. Both tools were run with the same
thread argument in each comparison.

Reproduce: `bench/run_all.sh`, `bench/run_big.sh`, `bench/run_final.sh`
(arrays are generated by `tests/gen_bench.py`; the four large arrays come
from `table/arrays/ (after their entry; before that, the item 75 working folder) `).

## The four t = 4 binary arrays (the hard case)

ca_verify2, two threads, full exact check, all four VERIFIED:

| array            | column sets C(k,4) | ca_verify2 CPU s | per column set |
|------------------|-------------------:|-----------------:|---------------:|
| CA_216_4_1368_2  |    145,286,988,210 |     243.8, 258.1 |   1.68, 1.78 ns |
| CA_224_4_1476_2  |    196,955,161,425 |            339.9 |        1.73 ns |
| CA_233_4_1596_2  |    269,331,050,835 |            485.5 |        1.80 ns |
| CA_242_4_1728_2  |    370,215,608,400 |            601.2 |        1.62 ns |

ca_verify on the same arrays cannot be timed to completion here. Its cost
per column set is independent of k apart from cache effects, so it was
measured on column-truncated copies of CA_216_4_1368_2 (one thread):

| columns | column sets | ca_verify CPU s | per set | ca_verify2 CPU s | speedup |
|--------:|------------:|----------------:|--------:|-----------------:|--------:|
|     150 |  20,260,275 |           13.53 |  668 ns |             0.22 |     62x |
|     200 |  64,684,950 |           39.31 |  608 ns |             0.55 |     71x |
|     300 | 330,791,175 |     (not run)   |         |             2.05 |         |

(The speedup grows with k because ca_verify2's work is proportional to
C(k,3) * N * passes while ca_verify's is proportional to C(k,4) * N; at
small k the chunk passes are short and the per-prefix overhead shows.)

Extrapolating ca_verify at 608 ns per column set (the k = 200 rate; the
k = 150 rate would give 10 percent more):

| array            | ca_verify CPU (extrapolated) | ca_verify2 CPU | speedup |
|------------------|-----------------------------:|---------------:|--------:|
| CA_216_4_1368_2  |          88,300 s = 24.5 h   |  243.8, 258.1 s | 342x to 362x |
| CA_224_4_1476_2  |         119,700 s = 33.3 h   |        339.9 s |  352x   |
| CA_233_4_1596_2  |         163,800 s = 45.5 h   |        485.5 s |  337x   |
| CA_242_4_1728_2  |         225,100 s = 62.5 h   |        601.2 s |  374x   |

Lower bound from the real run: the main session's `ca_verify` on
CA_216_4_1368_2 had consumed 2 h 59 min of CPU after 3 h 05 min of wall
time without finishing (checked at 00:33 UTC), consistent with the
extrapolation (about 12 percent through).

## t = 3, larger v (one-hot lane kernel)

Exact constructions (Bush orthogonal arrays over GF(25) and GF(5), Roux
doubling), plus one random array, all t = 3, both tools two threads:

| array                       | kind                   | ca_verify CPU s | ca_verify2 CPU s | speedup |
|-----------------------------|------------------------|----------------:|-----------------:|--------:|
| OA(15625; 3, 26, 25)        | Bush, covering         |            0.09 |             0.05 |    1.7x |
| CA(30625; 3, 52, 25)        | Roux doubling, covering|            2.03 |             0.56 |    3.6x |
| CA(15725; 3, 96, 5)         | Roux x4, covering      |            6.28 |             0.22 |     29x |
| 16000 x 150 random, v = 25  | every 3-set has gaps   |           54.17 |             6.32 |    8.6x |

For large v the per-row data (a 25-bit lane per column, 32-bit lanes) is
wide, and for the random array every class of every prefix takes the slow
path that counts and locates the 3.1e9 missing tuples; both tools report
identical counts and identical example lists. These cases take seconds
either way; the gain matters at t >= 4.

## t = 5 and t = 6, binary, k in the hundreds

Random binary arrays with enough rows to be covering (and they are):
900 x 200 at t = 5, 1900 x 100 at t = 6. ca_verify was timed on
column-truncated copies and extrapolated by C(k,t) (its per-set cost is
proportional to N and independent of k):

| array            | column sets   | ca_verify CPU s           | ca_verify2 CPU s | speedup |
|------------------|--------------:|--------------------------:|-----------------:|--------:|
| 900 x 60, t=5    |     5,461,512 |  15.48                    |             1.03 |     15x |
| 900 x 200, t=5   | 2,535,650,040 |  7,187 (extrapolated)     |           117.6  |     61x |
| 1900 x 40, t=6   |     3,838,380 |  26.62                    |             3.51 |    7.6x |
| 1900 x 100, t=6  | 1,192,052,400 |  8,262 (extrapolated)     |           469.4  |     18x |

These are the weakest cases for the method: with t = 6 the largest prefix
column is on average at 5/6 of the columns, so each (t-1)-prefix (whose
cost is proportional to N = 1900) is amortized over only about k/6
candidate columns. Classes are sparse here (N / (v^(t-1) W) about 2 rows
per bitset word), which is why ca_verify2 switches to its branch-light row
list extraction; walking the bitsets directly was 1.5x slower (613 s for
the t = 6 array).

## Scaling and other hardware (estimates, not measured)

ca_verify2's time is proportional to C(k,t-1) * N * (number of 256-column
chunk passes); for the four t = 4 arrays the measured per-column-set cost
is flat at 1.6 to 1.8 ns, so the fifth array of that family would be
predicted by its C(k,4). Threads split the smallest column dynamically;
the largest unit is 0.2 percent of the work, so near-linear scaling is
expected up to dozens of threads. Shards (`SHARD/NSHARDS`) partition the
same units deterministically; shard CPU times for CA_216_4_1368_2 with
four shards: see `bench/final_run1.log` (shard 0/4 of the work took
64.9 s of CPU, a quarter of the 258 s of the unsharded run made right
before it).

- GitHub free runner (4 x86 cores, AVX2): about 70 s for CA_216_4_1368_2
  and about 170 s for CA_242_4_1728_2 at four threads, if the cores are
  comparable to this Xeon.
- Apple Silicon (NEON, 12 threads): the same source compiles the 256-bit
  vector types to pairs of NEON operations; with roughly twice the
  per-row instruction count but higher IPC and clock, a few minutes at
  most for the largest array across 8 to 12 threads.
- Memory: the planes of a binary array are N * 32 * ceil(k/256) bytes
  (61 KB for CA_242_4_1728_2); the row bitsets k * v * ceil(N/64) * 8
  bytes; per thread v^(t-1) * ceil(N/64) * 8 bytes of class bitsets.

## Tests

- `tests/difftest.py ORIG NEW [count] [seed]`: random small arrays
  (random, greedy-completed covering, near-covering with exactly one
  missing tuple at a random position, don't-cares in all four token forms,
  0- and 1-based symbols, space/tab/comma separators, blank lines) plus
  wide arrays (up to 1100 columns, exact strength-2 Sperner arrays with
  and without don't-cares, random t = 3 arrays with 330 columns, random
  v up to 40). Each array is run with 1 and a random second thread count
  on both tools; stdout and exit code must be byte-identical, so the gap
  and missing-tuple counts and the ten example lines (which depend on the
  thread count) are compared, and a Python reference recomputes gap and
  missing counts for the small cases. Shards 2 to 4 of NEW must add up to
  the unsharded counts. NEW is also run with forced code paths
  (CA_VERIFY2_REP=planes|onehot, CA_VERIFY2_CLASSES=bitset|sort,
  CA_VERIFY2_ROWS=bits|list, CA_VERIFY2_KERNEL=base) so that every kernel,
  not just the one the heuristics choose, is checked against the original.
  Results: 3000 cases (seed 7, first version), 1200 cases (seed 21) and
  1500 cases (seed 33) with the final source: 0 failures; about 11,000
  paired runs, 2,400 shard checks.
- `tests/mutation_test.py ORIG SOURCE.c`: 18 single-point mutants of the
  source (wrong candidate mask, prefix bound off by one, dropped value-0
  test, wrong missing-tuple arithmetic in empty classes and in the slow
  path, rank off by one, shard partition overlap, don't-care read as 0,
  value-plane and one-hot kernels never reporting, counting sort placing
  wrong rows, unsorted examples, wrong chunk data in the four-chunk pass,
  shifted row bitsets, wrong first missing value, one-hot candidate mask
  including column c, dropped second chunk report, row-list extraction
  losing a row). Each is built and run on 78 arrays with 1 and 3 threads
  and 3 shards; all 18 are detected (disagree with ca_verify), and the
  unmutated source agrees on all arrays under every forced path.
